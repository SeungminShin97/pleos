| ID | 질문 | 필요한 증거·처리 |
| --- | --- | --- |

| Q05 | 이동 요청 완료가 실제 이동 완료를 의미하는가 | 반환·콜백 의미와 재조회 결과를 구분 |

| Q07 | 저장한 임의 위치를 재현할 수 있는가 | 조회·명령·정지·재조회로 성공·오차·한계를 기록 |

기술 미확정 사항은 '실패'와 '미시도'도 구분합니다. 접근 권한이나 환경이 없으면 미검증이라고 남기고 UI에서 해당 지원을 보장하지 않습니다. 검증 가능한 다른 부분은 계속 개발합니다.

## 적용·복귀 구현 시 유지할 설계

- 활성 세션을 한 개로 직렬화하고 중복 요청이 원래 스냅샷을 덮어쓰지 않게 합니다.
- 실제 쓰기 전에 선택한 항목의 현재 값과 실행 계획을 영속 저장합니다.
- 작업 상태는 PLANNED·DISPATCHED·CONFIRMED·FAILED·UNKNOWN을 구분합니다.
- 타임아웃·프로세스 종료 후 자동 재실행·반대 방향 이동 대신 실제 상태를 다시 확인합니다.
- 복귀는 앱이 바꾼 항목을 중심으로 처리하고 사용자가 수동 변경한 항목은 충돌 선택을 제공합니다.
- 기어 변화·알람·도착 이벤트로 좌석을 자동 복귀시키지 않습니다.
- 단위·범위·여러 축의 이동 순서를 차종 공통 상수로 추정하지 않습니다.
- 전체 상태 전이·화면·데이터·수용 테스트는 [DESIGN](DESIGN.md)의 3·4·8·9·10절을 따릅니다.

## 알람·음성 단계에서 유지할 조건

차량 알람은 OS 예약 API와 실제 오디오 출력을 검증합니다. 차량 전원 종료 후 지속을 보장하지 않습니다. 휴대폰에는 예약·변경·취소의 ID·revision과 실제 OS 예약 확인 응답이 필요하며, 중계 수신·푸시 도착만으로 완료 표시하지 않습니다.

앱 내 STT는 유한한 인식 세션부터 구현합니다. Gleo 진입은 상시 앱 마이크 점유와 구분합니다. 개인 호출어·사용자 녹음은 별도 인식 기술·권한·수명주기 검증 과제입니다. 음성 명령도 차량 상태 검사와 사용자 확인을 통과해야 합니다.
